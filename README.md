nfs_client.c

    Επιδι ο nfs_client.c λειτουργει σαν μινι server παμε και φταχνουμε σωστα τα sockets. Το θεμα ειναι οτι επειδι εχουμε να κανουμε με server σε περιπτοση που καποιο system call παει λαθος τοτε βγαζουμε αντοιστιχο μυνημα και τερματιζουμε το proccess.

    Οσο αφορα το 1ο conection μεταξη καποιου worker και καπιου client διαβαζουμε απευθειας ολο το μυνημα. Προσοχη υποθετουμε οτι ΠΑΝΤΑ αμμα θελει ο worker να κανει push θα αρχιζει παντα με "PUSH </somedir/somefile> -1'\0'". Με λιγα λογια οταν κανουμε το 1ο read σαν client και μας ερχετε PULL ειμαστε σιγουρι οτι δεν εχουμε μεσα καθολου δεδωμενα για διαβαζμα. Με αυτον τον τροπο εχουμε μια πιο κομψη υλοποιηση. Γενεικα διαβαζουμε με safe τροπο

client_thread.c

    Συναρτισεις που εχουν μεσα την υλοποιηση των threads. Ολα τα threads ειναι detach διοτι δεν μας νειαζει το αποτελεσμα τους + διευκολεινουν το flow. Ουσιαστικα φτιαχνονται κανουν μια σιγκεκριμενη δουλεια και μετα διαγραφονται.

    Ουσιαστικα για αρχη διαβαζουμε το μυνημα που μας σταλθηκε (πρεπει να γινει αναγκαστικα 1-1 byte διοτι, υπαρχει η περιπτοση να εχουμε PUSH με link κλπ και μετα να ακολουθουν απευθειας το chunk και τα data που θα πρεπει να κανει copy-paste). Αφου βρω την σωστη εντολη παω και εκτελω μια απο τις παρακατω 3 συναρτισεις

    (1)LIST. Με βαση την ρωη του προγραματος βασι της εκφονισεις ειμαστε σιγουροι οτι δεν υπαρχει περιπτοση να σταλθει και αλλο LIST απο τον μανατζερ αν πρωτα δεν εχουμε τελειωση ενα ειδι υπαρχον LIST ετειμα. Υποθετουμε οτι το directory υπαρχει οντος.

    (2)PULL. Με βαση την ρωη του προγραματος βασι της εκφονισεις δεν υπαρχει περιπτοση να πρεπει να διαβασουμε ταυτοχρονα 2 threads το ιδιο αρχειο

    (3)PUSH. Μετα το 1ο handshake το μονο που λαμβανουμε ειναι μυνηματα του στιλ <chunk size> <data>. Δεν εχει καποιο νοημα να ξαναλαμβανουμε το "PUSH /dir/file".


nfs_manager.c

    Ο manager κανει init τα structs ανοιγει sockets για αρχισουν να του ερχονται requerst διαβαζει το config για καθε φταχνει τα threads και μετα δεχετε requests. Αμμα κανει ADD και βαλει καινουρια πραγματακια στο QUEUE ενειμερωνει το FILLER. Αμμα κανει CANCEL παλει ενιμερωνει τον FILLER. Οταν παρει shutdown αλαζει μια κοινει μεταβλιτη για σε true και ενιμερωνει ολλους τους WORKERS και τον FILLER προκειμενου οταν τελειωσουν τις εργασιες τους να τερματισουν. Τελος αποδεσμευει τον χορο που καταναλωσε για τις δομες μας.

manager_threads.c

    Συναρτισεις που εχουν μεσα την υλοποιηση των threads.Εχουμε 2 ειδον threads 

    (1)Filler. Εχουμε ακριβος εναν filler. Η δουλεια του οπως το λεει και το ονομα του ειναι να γεμιζει. Ουσιαστικα περιμενει μεχρει να αδιασει ο ενταμιευτης (slots of tasks for the workers) και να εχουμε τουλαχιστον 1 task μεσα στο Queue. Οταν και οι 2 συνθικες ειναι αληθης παει και γεμιζει τον ενταμιευτει ειτε πληρος ειτε μεχρει να αδιασει το Queue.

    (2)Workers. Οι workers ειναι ουσιαστικα πανω απο ενας (ορισμα γραμης εντολων ή 5 defoult) και κανουν ακριβος της δυσκολη και χρονοβορα δουλεια της αντιγραφης αρχειων περνοντας chunks δεδωμενων απο ενα socket σε εναν ενδιαμεσο buffer και σπροχνοντας τα σε ενα αλο socket. Οι workers περιμενουν μεχρεις οτου να υπαρχει τουλαχιστον 1 κενη θεση στον ενταμιευτει για να παρουν το task απο αυτον.

    Τα κοινα δεδωμενα που υπαρχουν ειναι ο ενταμιευτης, το queue, ενας ακαιρεος για τις θεσεις του ενταμιευτη που ειναι γεματες και ενα path.

    Οι workers χρειαζονται προσβαση στο: path, τον ενταμιευτη και το αρηθμο γεματων θεσεων
    Ο filler χρειαζετε προοσβαση στο: ενταμιευτη, τον αριθμο γεματων θεσεων και το queue
    Ο manager aka main thread χρειαζετε προοσβαση στο: queue

    Με βασει τα παραπανω και εχωντας στον νου το ποτε θα γεινετε κατι thread_wait αλλα και την προσβαση που πρεπει να εχουμε + αποφιγη deadlock. Εχουμε μονο 2 mutex ενα που προστατευει (queue, ενταμιευτη, μεγεθος κενων θεσεων) και ενα που προστατευει την κοινη εγγραφη report στο logfile.


MESSEGES IPC

    Η επικινωνια γεινετε με την χριση των 2 βασικων συναρτισεων safe read και safe write ειναι στην ουσια ενα περιτλιχτης της read και write προκειμενου να γραφουμε και να διαβαζουμε ολα τα bytes που θελουμε. Γενεικα εχω καποια perror στην περιπτοση που και παει λαθος. Αλλα γενεικα δεν υπαρχει ποτε τετεια περιπτοση. Λογο τις σχεδιασης που εχω κανει δεν θα διαβασω ποτε σε ενα socket το οποιο εχει κλιση απο την αλη ακρη ή αμμα διαβασω θα εχει μεσα δεδωμενα. Επιδι ξερω στην ουσια ποτε τελειωνουν τα δεδωμενα που θελω να διαβασω. Ακομα δεν υπαρχει παλυ ποτε περιπτοση να γραψω σε εναν socket οπου το αλο ακρο ειναι κλειστο. 

    MANAGER --> CLIENT first handshake: raw message with '\0'
    MANAGER --> CLIENT PUSH error: 0 whitespace '\0'
    MANAGER --> CLIENT PUSH fine: chunksize whitespace data
    CLIENT --> MANAGER LIST respones: raw message with '\0'
    CLIENT --> MANAGER PULL error: (file size, string) whitespace (error message) '\0' 
    CLIENT --> MANAGER PULL fine: raw message with '\0'

    CONSOLE --> MANAGER operation: raw message with '\0'
    MANAGER --> CONSOLE ADD problem (nalready sync): raw message with '\0'
    MANAGER --> CONSOLE ADD done: raw message '\n' raw message '\n' .... raw message '\n' '\0' (for every file we add)
    MANAGER --> CONSOLE CANCEL problem (no sync) : raw message with '\0'
    MANAGER --> CONSOLE CANCEL done: raw message '\n' raw message '\n' .... raw message '\n' '\0' (for every dir with diferent ip:port)
    MANAGER --> CONSOLE shutdown: raw message '\n' raw message '\n' raw message '\n' raw message '\n' '\0'

Ενταμιευτης

    Ο ενταμιευτης ειναι στην ουσια ενα πινακακι με δικτες σε nodes της QUEUE αυτο εγεινε σκεμενα προκειμενου να μην χριαζετε να δεσμευω πολυ χορο ξανα και ξανα για να κανω απλα copy-paste ενα task που βγαζω απο το QUEUE και θελω να το βαλω στον ενταμιευτη. Τωρα απλα το κανω να διχει σε μια διευθινση μνημης.
